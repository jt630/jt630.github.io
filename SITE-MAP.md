## Grouping rationale

PR-B split the old 13-item Ops group (junk-drawer per the structure-remodel
review) into two:

- **Live Data** (7): Dingers, Beer Sheet, Markets, Calendar, APIs, Auction
  Watch, Grandpa's Shop — every page here is an auto-updating dashboard or
  tracker, not a one-time write-up. Auction Watch and Grandpa's Shop sit
  together because they're already a parent/child data pair.
- **Life Admin** (6): Gadgets, Body, Backpacking, Car Hunt, The Forester,
  Garage — personal-logistics pages. The vehicle timeline (Car Hunt →
  Forester → Garage) is kept contiguous and in chronological order so
  PR-C's Wheels hub can reuse the same ordering; Car Hunt is marked done
  (bought the Forester 2026-09-09).

These are proposed names, not a locked decision — easy to rename in
hugo.toml if they don't stick.

## Hubs

The mechanism (PR-C): a hub is `content/hubs/<name>.md`, with front matter
`members: [{path, note?}]`. `layouts/hubs/single.html` resolves each path
with `site.GetPage` and calls `errorf` if one doesn't resolve, so a renamed
or deleted member page fails the build instead of silently dropping off the
hub. `layouts/partials/hub-backlink.html`, included once in
`layouts/_default/baseof.html`, derives the "Part of X" link on every
member page — nothing is hand-written on the member side, so a renamed hub
or a member added/removed never needs a second edit. `content/hubs/_index.md`
gives `/hubs/` a free index of every hub, which the homepage's Connections
strip also links as "See all". Verified with a negative test: pointing a
member at a bad path made `hugo` fail with the `errorf` message before the
mechanism was trusted; the bad path was reverted after confirming the
failure.
